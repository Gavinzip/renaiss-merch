# Surf VRF 逾時重抽

## 原因與邊界

2026-10-16 的第一輪請求交易已確認，但 Binance Oracle 未回覆。原合約的
`resetDraft(drawId)` 在 `RandomnessRequested` 狀態會拒絕，所以原輪不能直接清空。
這不是再次點擊「請求 VRF」可以修復的狀態。

已決定沿用 `RenaissLuckyDraw` 和結果合約，以新的 draw ID 建立第二輪。第一輪
請求、帳本及交易仍留在鏈上和 Zeabur 持久化資料庫；正式網站只讀目前啟用的
第二輪，並在驗證資訊標明第一輪作廢時的鏈上區塊與請求交易。

## 操作

1. 在本地 `/draw/#draw/surf` 登入開獎室。
2. 「作廢舊輪並建立新輪」只在舊輪仍等待 VRF、原請求交易已確認且超過
   256 個區塊、新輪尚未使用時出現。確認後，它在 Zeabur 掛載的資料庫內複製
   原先鎖定的 2,434 筆參加者、6,506 張票及聯絡資料快照，只有 draw ID
   和帳本承諾雜湊改變；不重新讀取目前名單，不送鏈上交易。
3. 核對第二輪的參加人數、票數、27 個獎位和新帳本雜湊，再按「提交已確認帳本」。
4. 提交交易確認後，按一次「請求 VRF」。如果協調合約拒絕新的請求，交易估算
   會先失敗，不會廣播。等待新請求的回覆；之後的揭露不再重新抽亂數。

2026-10-16 的唯讀 `eth_call` 已確認：舊請求仍讓訂閱的
`pendingRequestExists` 回傳 `true`，但同一協調合約仍接受該已註冊消費者的
另一筆 `requestRandomWords` 模擬。因此網站不再把「訂閱有任何待回覆請求」
當成新輪的全域鎖；仍檢查新輪狀態、訂閱餘額和交易估算。
